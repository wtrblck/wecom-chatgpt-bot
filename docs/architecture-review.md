# 架构评估与重构记录

日期：2026-09-06。目标：个人微信群文字 → GPT 网页 → 原群；用户明确要求保留 GPT 网页，并优先考虑稳定性、速度。

## 结论

影响可靠性的首要问题是消息状态与操作结果缺乏闭环，其次才是鼠标坐标。新的收件箱和发件箱可以保留并迁移到任何微信传输方案；微信发送层必须独立验证具体客户端兼容性。

当前主机微信 4.1.13.12 默认缺少聊天 UIA 控件。经用户明确授权，独立 helper 严格核验候选并启用可访问性后，节点从 6 增至 167。实测按钮 Invoke 不提交，最终采用 UIA 目标/焦点核验加单次 Enter，约 1009ms 获客户端提交回执，数据库仅匹配一条。公开资料没有足以直接采用的本版本成熟按群 ID 发送接口，所以没有贸然更换为 Hook。

## 原实现的问题与落地改动

| 原问题 | 后果 | 本次改动 |
| --- | --- | --- |
| 个人微信仍强制填写企业微信凭据 | 安装和启动步骤无关且繁琐 | 企业微信显式启用；默认个人微信、DB、前缀触发 |
| Python poll 写水位早于 Node 接收 | IPC/处理出错后漏消息 | poll/ack 两阶段协议；收件箱事务提交后 ack |
| 只用 sort_seq，读取首个消息分片 | 同序号边界、跨分片可能漏读 | 所有分片正序合并，复合游标分页 |
| sender_id 固定等于 2 判为自己；资源库与消息分片的数字 ID 混用 | 回环、误过滤或无法确认发送者 | 在各消息分片自身 Name2Id 映射真实 sender wxid，与登录账号比较 |
| 按模糊名字选择群 | 相近或重名群可能发错 | 精确解析、唯一名称、已配置稳定 ID 不回退同名 |
| 去重标记先写，task 后写 | task 创建失败但永远不重试 | 普通问题及任务型 /retry 的 claim/create 同事务 |
| 重启不恢复 queued | 永久排队 | 收件箱保留消息上下文，可重建 queued；不可恢复的旧任务标 aborted |
| 生成答案只在发送成功后保存 | 发失败就丢答案，只能再问 GPT | 先保存答案；重启/重试优先补发 |
| 发送完才释放 GPT 队列 | 一次慢 UI 发送拖慢全局 | 生成与发送独立；离线测试证明慢发送不阻塞下一次 generate |
| 分片逐个 enqueue | 段落交错、间隔失效 | 一整个回答占用 worker，片段间节流并独立记录状态 |
| 桥接超时只删 Promise | 超时后仍可能迟到发送 | 直接运行原生 worker；超时终止整代 worker，旧回调不污染新代 |
| 发布目录 v24/v2 文档实现不一致 | 实际跑旧二进制 | 固定 publish，协议版本校验，缺失明确要求 build |
| 鼠标粘贴/Enter 缺少核验 | 焦点错误、草稿混入、发送设置差异 | UIA 目标标题/输入/前台/焦点验证，一次配置的提交动作，禁止自动后备 |
| GPT 文本静止 8 秒即返回，即使 Stop 可见 | 思考/检索被截断 | Stop 可见时绝不提前完成；超时尝试停止生成 |
| GPT 点击与确认封装为整体重试 | 已发送但确认迟到时重复提问 | 提交动作一次；确认失败标记未知，不自动再次提交 |
| 根 URL 未改变就复用页面 | 临时会话/未保存会话可能串群 | 新会话强制导航并拒绝残留历史；既有 URL 校验重定向 |
| 安装缓存和临时文件散落用户目录 | 环境难清理、难迁移 | 统一项目运行入口和安装脚本，项目内环境与缓存 |

## 速度取舍

1. 使用 DB 读取所有配置群，避免逐群打开窗口、OCR 和复制，默认 1 秒轮询。本机两次短回复从程序入站至客户端提交约 8.35 秒、10.46 秒，其中网页处理占主要时间。微信 create_time 与本机日志观察到时钟/语义偏差，不能直接相减当作收件轮询耗时，也不能把 1 秒轮询等同于 1 秒端到端延迟。
2. GPT 单页串行：保留页面操作互斥与群上下文隔离。微信回复已独立执行，去掉网页等待发送的额外时间。
3. 不再为每条排队问题向微信发送“已收到”，减少窗口操作与群噪声。
4. 发送后只在必要位置节流；未确认结果不重试。盲目缩短等待或并行操作同一窗口可能让平均速度变快而故障率升高。
5. 暂不引入多 GPT 标签页并发。它需要额外处理账号并发、页面归属、取消和限流，不能只把全局锁删除；如未来压测证明 GPT 排队是瓶颈，可在单群串行前提下引入小规模标签池。

## 恢复语义与边界

入站为可重放加持久去重；网页和微信 UI 并不支持真正的 exactly-once 提交事务。程序在提交后崩溃时只能保留未知状态并要求核验，不能同时保证不漏发和不重复。

首次新增监听从最新记录之后开始；旧水位升级保守重放边界，由已有 messageId 去重。数据库账号与水位绑定；更换账号需独立缓存，不能复用另一账号的进度。

未生成 queued 可恢复。已保存答案且未出现未知发送片段，可安全重新进入发送队列。生成中的任务重启后标 aborted，不自动再次向网页提交。恢复 queued 的 /retry 按原问题重新提交，未持久化旧页面 regenerate 控件操作。

网页端的“系统提示词”只是用户消息前置文本，不能提供 API system 角色的优先级。文本式 `@昵称` 不等于微信原生提醒。

长期驻留仍依赖 Windows 解锁、客户端版本、ChatGPT 登录有效性和页面结构。当前数据表没有自动过期清理；故障时保存的截图/HTML、缓存、收发件箱都应按本地敏感数据保管。

## 验证

类型检查、Node 构建、原生桥接构建与离线故障注入测试已执行。测试覆盖跨分片分页、ack 失败、崩溃重放、发送不确定、部分成功、旧进程退出竞态、长时间生成停顿、群会话隔离与慢发送解耦。

用户授权后已激活可访问性、完成 GPT hello 和两次指定测试群的完整往返，DB 均核对到唯一回复；还验证停机期间消息的重启续读及本地停止命令。完整结果见 [验证记录](validation.md)。长回复、多群排队、生成中取消和断网恢复主要由离线测试覆盖，不能用少量冒烟测试推断长期在线故障率或真实吞吐量。
